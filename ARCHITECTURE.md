# Архитектура и границы исходников

`me.skywars2.SkyWars2` подключает серверные системы. Реализация игры находится
под `me.skywars2.game`, Mixin — под `me.skywars2.mixin`. Классы распределены по
предметным областям; Java-пакеты соответствуют каталогам.
[Карта исходников](docs/SOURCE_LAYOUT.md) содержит дерево и примеры классов.

## Сервер и проверки

`src/main/java` содержит только обычную серверную реализацию. Общие типы
телефона из `media-protocol/src/main/java` компилируются в тот же артефакт.
Нативные проверки и реализация редактора карт находятся в `src/checks/java`.
Они используют классы основной сборки через отдельный Gradle source set `checks`.

Проверки могут сохранять пакет проверяемой системы для доступа к её внутренним
типам. Физическое разделение исходников исключает их из обычного серверного JAR.

`productionJar` создаёт обычный мод. `testServerJar` добавляет к готовому
серверному артефакту проверки и их метаданные. Общие ZIP-записи, кроме намеренно
дополненного `fabric.mod.json`, должны оставаться идентичными. Тестовая версия
сохраняет вложенные зависимости и отдельно подключает validation Mixin.

## Предметные пакеты

`game/items/phone` объединяет серверную реализацию телефона: аккаунты и импорт,
подготовку очереди, воспроизведение, изображение, звук и передачу клиенту.
Соответствующие нативные проверки лежат под тем же Java-пакетом в `src/checks/java`.
Общий сетевой транспорт обращается через публичную границу `TikTokClientSupport`;
внутренняя очередь вывода `TikTokOutput` остаётся внутри пакета телефона.

`game/genie` и `game/genie/script` содержат службы джина и интерпретатор предметов.
Остальные семейства расположены под `items`, `entities`, `effects`, `academy`,
`gui`, `world`, `match`, `players`, `skills`, `net` и `commands`. В корневом `game`
остались три общих контракта: `GameController`, `LbcItems` и `NativeCheckHooks`.

## Перенос классов

Используйте [семантический инструмент JDT](tools/JAVA_REFACTOR.md): он обновляет
пакеты, импорты и Java-ссылки. Отдельно обновляйте имена в Fabric/Mixin JSON,
строковые Mixin targets и пути классов, используемые инструментами.

```powershell
python -B tools/check_java_layout.py
```

Проверка сверяет каталог с декларацией пакета, границу production/checks,
регистрации Fabric и Mixin, включая вложенные классы. Она также поддерживает
`--repo PATH` для отдельного worktree. После переноса нужны компиляция обеих
сборок и соответствующие нативные проверки.

В установленной версии JDT массовый перенос иногда теряет внешнего владельца
вложенного типа: `Outer.Image` превращается в несуществующий `package.Image`.
Такие ссылки восстанавливаются по исходной Java-привязке и месту использования,
а не по совпадению имени `Image`. При расширении доступа к записи её явный
канонический конструктор также должен иметь подходящий доступ. Поэтому успешный
ответ инструмента дополняется проверкой компиляции, регистраций и байткода.

Идентификаторы предметов, таблиц лута, переводов, сохранений и сетевых пакетов
при таком переносе сохраняются. Игровые исправления оформляются отдельно от
изменения расположения классов.

## Подробные контракты

Развёрнутые описания сохранения состояния матча, сущностей, очередей, эффектов
и прошлых переносов доступны в
[архитектурном справочнике](docs/history/ARCHITECTURE_2026_11_21.md).
Там же сохранены ограничения экспериментального восстановления нативного ИИ:
перемещение его исходников не включает эксперимент в обычной игре.

Дополнительный клиент телефона собирается отдельно в `media-client/`, используя
общий протокол из `media-protocol/`. Изменение пакетов серверной реализации
не должно менять этот протокол или требовать клиентского мода для обычной игры.
