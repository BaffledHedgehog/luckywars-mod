# Chest marker source audit

This began as a read-only comparison of the legacy `swarogskywars` datapack and Fabric `MapManager`. The later map35 regression case is listed below. Current loader changes and verified behavior are documented in [CHEST_LOOT_SPILL_FIX.md](CHEST_LOOT_SPILL_FIX.md); no original world or map files were changed.

## Marker contract in the legacy datapack

- `data/swrg/predicate/core/chest.json` selects entities by tags `swrg.center`, `swrg.midle`, or `swrg.default`; it does not constrain the entity type itself.
- The actual refill selectors in `data/swrg/function/game/chests/fill.mcfunction` are stricter: they use `@e[type=minecraft:marker,...]`. They clear `Items` at each qualifying marker position; place a chest if that position is not already in the `#chest` block tag; assign `swrg:chests/default`, `midle`, or `center`; then apply `swrg:empty` and run count normalization.
- `data/swrg/function/game/start/1.mcfunction` invokes this refill at match start. Stage-one refill events also clear/reassign loot. `game/stage1/event6.mcfunction` upgrades default/midle marker tags to `swrg.center` before calling the refill. Therefore chest marker entities are data/control points, not decorative entities: the required map anchors are `minecraft:marker` at each chest block with one of those three tags.
- `data/swrg/predicate/core/lobby.json` explicitly preserves any entity carrying those chest tags (as well as `swrg.look`, `swrg.spawn`, `map_object`, and `strict_map_object`). `maploader/clear1.mcfunction` kills `strict_map_object`, then maploader-tagged entities, then repeatedly kills all entities not passing the lobby predicate. Thus the generic legacy transition cleanup does not remove correctly tagged chest markers. `maploader/clear.mcfunction` uses `swrg.clear` marker positions for block clearing; these are temporary clear-work markers, not chest anchors.

## Current loader and refill behavior

- `MapManager.finishPlacement()` collects all entities within the placed template bounds, extracts `swrg.spawn` and `swrg.look` positions, and sets the active bounds. It does not require a specific entity class for the positional tags.
- `MapManager.fillChests(boolean)` iterates all arena entities, immediately skips every entity that is not a vanilla `Marker`, then recognizes the same three chest tags. It creates a chest if needed, clears the block entity contents, assigns the chosen loot table lazily, generates it, and normalizes legacy synthetic item counts. A `block_display` with `swrg.center/default/midle` is therefore not a chest anchor and will never refill a chest at its position.
- The lobby entity audit keeps all entities inside loaded map bounds, then keeps the explicit lobby/map tags outside those bounds. This means a map's technical `block_display` remains with the map while that map is loaded; it is not silently converted into or substituted for a `Marker`. Airdrop entities tagged `skywars2.airdrop` are discarded from lobby preservation.

## Causal assessment and entity handling

A saved technical entity at a chest coordinate is not sufficient to drive chest creation or loot refill unless it is a `minecraft:marker` with the right chest-category tag at the chest block position. The legacy developer overlay shown by `developer/markers/5t.mcfunction` is specifically `minecraft:falling_block` (concrete `BlockState`), with entity tag `marker`, `NoGravity:1b`, `Time:1`, and often `Invulnerable:1b`/`Glowing:1b`; these are not `block_display` entities. The function places green/red/light-blue concrete falling-block visuals at the default/midle/center anchor positions, plus yellow/white at spawn/look positions. The corresponding developer `markers/off.mcfunction` kills `@e[tag=marker]`, and `maploader/clear1.mcfunction` kills entities failing the lobby predicate. The lobby predicate does not whitelist the generic `marker` tag or `minecraft:falling_block` type, so these developer visuals are eligible for cleanup while the underlying correctly tagged chest `minecraft:marker` anchor survives. `markers/5t.mcfunction` schedules itself again every 5 ticks, so if the developer overlay remains enabled, its next run can recreate visuals for surviving anchors after cleanup. Keep intentional template `block_display` visuals within loaded map bounds; retain valid chest marker anchors through map/lobby transitions; treat the falling-block overlay as temporary developer visualization and clear it when disabling the overlay / transitioning. Discard unrelated transient entities and airdrop carts from the prepared map/lobby state as current cleanup does.

The code path proves that missing/wrong-type markers cause chests to be skipped by `fillChests`; it does not by itself prove that this caused the reported loot to be dropped on the ground. If loot was physically ejected at match start, inspect the map's chest block entity NBT and any item entities created during load/refill: the source behavior here clears chest contents and writes a loot table, while the visual `block_display` is not processed as a chest. The exact map template NBT was not inspected in this bounded audit (the parent agent is scanning the affected map), so the observed entity types/tags at reported coordinates were not independently verified. I found only a 26.3 local Minecraft sources jar and a Paper 1.21.11 server jar; neither establishes exact 1.21.4 falling-block landing behavior. `Time:1` maps to the falling entity age field (`timeFalling`) in the Yarn 1.21.4 API; the developer loop resets that age every five ticks. The summon command itself does not remove its source block. Whether these no-gravity entities can subsequently land/place at an anchor and affect a chest is not established here; do not attribute item drops to them without runtime or map evidence. See [Yarn 1.21.4 FallingBlockEntity API](https://maven.fabricmc.net/docs/yarn-1.21.4%2Bbuild.4/net/minecraft/entity/FallingBlockEntity.html).

## Map 35 structure evidence

The current map catalog identifies map `35` as four strict, full-integrity placements: `swrg:35-6`, `35-7`, `35-10`, and `35-11`. The audited map structures contain 29 native marker anchors total: 8 `swrg.spawn`, 1 `swrg.look`, 8 `swrg.default`, 8 `swrg.midle`, and 4 `swrg.center`. They also contain 29 technical concrete entities tagged `marker`; these are `minecraft:falling_block`, not `block_display`. The `map-editor-cleanup` GameChecks case requires those exact native anchor counts, no marker-tagged falling block/block display surviving map cleanup, no ground item entities on map load, and no newly spawned item entities during two consecutive chest refills. Each refill must leave all 20 chest marker containers present and nonempty.
