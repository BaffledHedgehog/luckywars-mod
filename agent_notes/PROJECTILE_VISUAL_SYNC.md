# Синхронизация Terra display и попаданий

Наблюдение пользователя и правило находятся в [AGENTS.md](../AGENTS.md).
Источники: [нативная интерполяция](PROJECTILE_DISPLAY_NATIVE_AUDIT.md),
[остальные визуалы](PROJECTILE_VISUAL_SOURCE_AUDIT.md).

При создании `attachModel()` задаёт направление из реальной velocity через
существующий `syncModel(position())` **до** создания `EntityAttachment`.
Polymer может сразу подключить уже отслеживающих сущность игроков внутри
конструктора attachment и отправить `ClientboundAddEntityPacket`. Его
начальные yaw/pitch должны быть готовы к этому моменту; поздняя корректировка
давала один кадр с нулевым поворотом. До attachment вызов `holder.tick()`
ничего не отправляет. Ориентация и transformation задаются общим кодом для
всех Terra-вариантов, новых обработчиков движения нет.

`LbcTerra.step()` сохраняет авторитетное попадание по физическому отрезку
`from..end`: поиск целей, столкновения, урон и игровое положение не используют
визуальное упреждение. Перед перемещением сохраняется текущая мировая позиция
display (`display.getCurrentPos()`); после установки физической позиции строится
новая визуальная цель и синхронизируется display. Частицы теперь проходят от
сохранённой визуальной позиции к этой же визуальной цели. Поэтому они следуют
за обновлённым дисплеем, а не остаются на один обычный шаг позади него.

В обычном режиме визуальная цель прогнозирует один следующий шаг по прежней
проверке стены и щита. Это только визуальная трассировка: она не ищет цели,
не наносит урон и не создаёт растения. Конечный снаряд не показывает прогноз
за пределами последнего шага. При столкновении цель остаётся в физической точке
контакта.

При `/tick freeze` физические снаряды не продвигаются менеджером, а клиентские
неигровые сущности не тикают: нативный `TickRateManager.isEntityFrozen()`
замораживает их, и `ClientLevel.tickEntities()` пропускает их `tick()`. Пакеты
перемещения при этом всё ещё обрабатываются клиентом; значит, уже установленная
интерполяция display не получает обычных клиентских тиков, пока игра заморожена.
Это подтверждённое объяснение риска рывка/задержки при пошаговой отладке, но
исходники сами по себе не доказывают потерю конкретного кадра в наблюдении
пользователя.

Код распознаёт замороженный режим через серверный `tickRateManager.isFrozen()`.
В нём визуальное упреждение отключается, `teleport_duration` переключается
с 1 на 0, а Polymer принудительно отправляет абсолютные координаты. В обычном
режиме упреждение и `teleport_duration=1` возвращаются. `interpolation_duration=1`
остаётся параметром интерполяции трансформации модели; он не задаёт движение
display-сущности. Отдельные состояния владельца (`time_stopped`) и внутриигровой
остановки времени не подменяются vanilla `/tick freeze`.

Holder создаётся с `EntityAttachment(..., false)` и обновляется вручную через
`holder.tick()`. При терминальном попадании он переводится на
`ManualAttachment`, чтобы display остался в точке контакта после удаления
игрового снаряда. Визуальная модель живёт ещё два manager ticks: один для
интерполяции и один для конечного кадра; очередь чистится и без летящих
снарядов и полностью уничтожается при остановке матча.

Дополнительная работа на шаг — короткая block DDA и проверка щита; урон и
поиск целей остаются однократными проверками авторитетного сегмента. Серверные
проверки состояния и координат не подтверждают порядок кадров настоящего
клиента. На изолированном сервере build и 13 сценариев прошли на JAR
`ca403de4…`. Восемь последовательных разрешённых шагов через настоящий
GameController с native freeze/step-флагами двигают физику и отправленный
display ровно на 1,8 блока; замороженные outer ticks не двигают их, а
разморозка восстанавливает duration=1 и прогноз. Основной сервер пока
работает с прежним JAR. Подробные результаты, границы проверки и готовая
сборка — в [SERVER_TESTS.md](../SERVER_TESTS.md).
