# Обычный Exasperato — исходный datapack

Исследован только базовый выстрел Exasperato (spell 199 / `click`), не улучшенные режимы. Источник — старый datapack `E:/servers_mew/cringe1_21_4_skywars/world/datapacksdisabled/LBC/data/lbc` (только чтение).

- Обработка основной руки проходит из `function/items/spells.mcfunction` через `function/workingitems/spell1.mcfunction` в `spell1_default.mcfunction`; вторая рука — через `spell1_left.mcfunction` в `spell1_default_left.mcfunction`. Суффикс `left` обозначает руку, а не левую кнопку мыши. Оба leaf вызывают `exasperato/click` при достаточной мане и отсутствии `stopper_magic` в радиусе 20. Стоимость — `exasperato_wand_mana_use = 1500` в `function/config.mcfunction`. `click` вызывает `click2`, снимает ману и применяет бонус полного mage-набора.
- `click2` создаёт marker в точке исполнения с `lifetime:200`, тегами `exasperato,rare,slowraycast,magic`, копирует Rotation, `lbcID2` и `team_number` игрока; для предмета с `upgradable:1` добавляет `check_upgrade`. Выстрел сопровождают три звука взрыва.
- Фактическая диспетчеризация: `function/raycastselector.mcfunction` прибавляет `Lifetime` на 1, затем вызывает `raycastselector_rare`; тот отправляет тег `exasperato` в `chtick`. Это одна обработка и один шаг за тик: `tp @s ^ ^ ^1` перемещает marker ровно на 1 блок вперёд. Далее идут частицы; TTL сверяется после обработчика, и при `Lifetime >= data.lifetime` marker убивается (`raycastselector_kills`). Следовательно, верхний предел — 200 обработок/блоков, если раньше не сработало попадание; при непрерывном тике это около 200 тиков. Время может растянуться, если dispatcher не вызывается.
- После шага есть две последовательные проверки срабатывания. Любой текущий блок, не входящий в `#minecraft:airs`, немедленно вызывает `chtick_explode`. Затем проверяются сущности `#minecraft:mobs`, `tag=!spectator`, селектором `dx=0,dy=0,dz=0,distance=..15`. В Minecraft 26.3 `EntitySelectorParser.createAabb(0,0,0)` строит AABB от текущей позиции до `(x+1,y+1,z+1)`: это куб 1×1×1 с верхними пределами координат плюс 1, а не точка. Поэтому для триггера тело сущности должно пересечь этот куб; дополнительно действует селекторная проверка `distance=..15`. При обнаружении `chtick_explode_check_id` помечает `nodamage` сущностей, совпавших с владельцем по `lbcID2` ИЛИ по `team_number`; только если остаётся хотя бы одна сущность без `nodamage` вызывается взрыв. После проверки глобально снимается `nodamage`.
- `chtick_explode` при `check_upgrade` и не менее 10 мобах в радиусе 12 выполняет побочный вызов `magic_academy/can_upgrade` для владельца с выбранным предметом `upgradable:1,exasperato_wand:1`. Затем создаёт 85 TNT: шесть осевых линий с шагом 0,5 блока до 7 блоков включительно, с общим началом (15 точек на первой оси и по 14 новых на остальных пяти). Каждый TNT задаётся SNBT `{fuse:2s}`: это short со значением **2 тика**, не 2 секунды. Следующей командой создаётся молния при максимум 50 выбранных TNT в радиусе 7,5 (`execute at @e[type=minecraft:tnt,...,limit=50]`), то есть до 50 lightning bolt за запуск; затем убивается marker луча.
- Урон — от нативных TNT-взрывов и нативных lightning bolt; в datapack-командах нет общего `damagewithid` или явного урона. Проверен Minecraft 26.3 source jar: TNT создаётся без `owner`; его нативный взрыв использует `Explosion.getDefaultDamageSource(level, this)` с самой TNT сущностью как источником. Lightning bolt вызывается без `cause`; нативный `Entity.thunderHit` наносит 5 урона через `damageSources().lightningBolt()` и поджигает сущность. Значит, ни одному из источников не передаётся игрок-кастер. Убийственная атрибуция старым datapack не сохраняется (ограничение datapack; см. `INDIRECT_KILLS.md`). Союзный фильтр применяется только к триггеру попадания по сущности. Попадание в блок не фильтрует команды взрыва, а сами TNT/молнии не исключают союзников или владельца из своих областей действия. Нельзя считать их защищёнными от побочного урона.

## Неопределённости

- Серверный прогон не выполнялся. В Minecraft 26.3 source `PrimedTnt` уменьшает fuse на 1 за tick; унаследованный `Entity.thunderHit` не меняет fuse (поджигает сущность и вызывает lightning damage). Это подтверждает заданный двухтиковый счётчик на уровне исходника, но не фиксирует фактический порядок обработки сущностей в tick на целевом сервере.
