# Artifact colors: state and team dependencies

Read-only dependency audit for the old LBC color artifact family and the current Fabric game classes. This records source behavior and port limits; it does not claim these effects are implemented.

## Mana and food counter source behavior

The color aura dispatches once every 5 ticks while the holder qualifies (`players_5t.mcfunction` -> `other/artifact/afkartifact5t.mcfunction` -> `other/artifact/colors.mcfunction`). A persistent state model must support repeated calls, since neither score is an ordinary vanilla stat.

- `other/artifact/colors/magenta.mcfunction`: add 20 to holder `mana`; copy holder `team_number` to fake score `*tempt lbcID2`; remove 20 from players 0.01..35 blocks away only when their mana is at least 20 and `predicate=!lbc:same_team`; witch particle. There is no mana maximum clamp in this function. Repetition can add/drain every five ticks.
- `other/artifact/colors/brown.mcfunction`: give holder Saturation with command duration 1, amplifier 1; increment `food_count` by 1; clear holder Hunger; copy `team_number`; apply Hunger to players (including mobs excluded by selector: `@a`) in 0.01..25 blocks, non-spectators, not same team, duration argument 30 seconds = 600 ticks, amplifier 1; cooked-beef particles and burp sound. In the old MC 26.3 command implementation, Saturation is instant and duration 1 means 1 tick.

`food_count` is not the vanilla hunger meter: old `other/food_counter.mcfunction` increments it on its own; `workingitems/witch_gens/gluttony.mcfunction` tests for 64+ and compares eligible players' counts; `workingitems/witch_gens/vanity.mcfunction` and `vanity_respawn.mcfunction` copy it to/from a marker. Old `load.mcfunction` declares `mana`, `manaregen_visual`, `manamax`, `manaregen`, and `food_count` as dummy objectives. Old mana is a subsystem, not a single scalar: regen code derives `manaregen_visual`, adds it to `mana`, clamps to `manamax`, and `reverse_mana` can gate regen. Spells and wands subtract configured mana costs; gear, effects, foods, crafting, and trinkets change mana/max/regen. Reproducing only the Magenta arithmetic would create an isolated counter that cannot be consumed or shown like the old stat.

## Current project mapping and limits

`PlayerStore.Profile` persists account selections, statistics, and unlocks; it has no in-match mana or food counter. `LbcItems` stores per-item transient state (e.g. item cooldown/state maps), not player LBC resources. `LbcSkills` and `MatchEvents` implement the current vanilla kit/skill and match event features, with no mana system. `GameController.Participant` currently stores spawn, lives, respawn, and connection state; it has no team number. The new game therefore has no ready team bridge equivalent to the legacy `team_number` + `lbc:same_team` scoreboard predicate.

Brown's native hunger clearing and Hunger effect are implementable using vanilla player state/effects. Faithful `food_count` increment still requires a new, explicitly scoped per-player in-match counter (or a ported shared LBC state model); do not alias it to hunger level or food exhaustion. Magenta similarly needs a defined shared mana state and consumers before it can be represented faithfully. `PlayerStore` is durable account storage and is not a ready substitute for short-lived match resource state. A Java-only visual bar or scoreboard bridge without the old regen, caps, spell costs, and item consumers would overstate parity.

The participant roster can identify match members, and vanilla `Entity.isAlliedTo` exists for Minecraft-native alliances, but the current participant setup does not establish teams. For solo matches, all opponents are enemies; in teams/modes where teams are introduced, preserve their actual assignment and exclude teammates. Avoid treating the current no-team solo semantics as proof of a team system.

## Purple cross-check

`other/artifact/colors/purple.mcfunction` applies `minecraft:raid_omen` for command duration 30 (600 ticks), amplifier 40, to non-spectator mobs at 0.01..20 blocks that fail the same-team predicate. The same function then repeatedly invokes native `spreadplayers`: centered at the holder with range 0..200 when `no_borders != 0`; centered at 0,0 with range 0..190 when `no_borders == 0`; Nether variants use `under 120`. Because dispatch repeats every 5 ticks, spreading repeats. Current match code already has native world-border and teleport/position handling for match phases, but not a color-artifact helper. Native `spreadplayers` remains an available command route; ensure it only moves the holder and honors the source's dimension/no_borders branches. Check how the new match maps world bounds before assuming the legacy global center is suitable.

## Narrow lifecycle audit: mana and food counter

Old `load.mcfunction:126-129,139` creates `mana`, `manaregen_visual`, `manamax`, `manaregen`, and `food_count` as dummy objectives. Default player values are applied by `resets.mcfunction`, which is called from three observed paths: `start.mcfunction:1` applies it to all players at match/game start; `other/new_game/click.mcfunction:11` applies it to all players on new-game selection; `other/idgive.mcfunction:5` applies it to an individual player when they lack the assigned `lbcID2` (that function is reached from `players_1s.mcfunction`). `resets.mcfunction:46-49` sets `manamax=5000`, `mana=5000`, and `manaregen=10`, except `SurvivalVersion=1` sets regen to 1. `resets.mcfunction:74` sets `food_count=0`.

Mana regeneration is a per-player tick path, not a one-second timer: `mobs_tick.mcfunction:4` calls `players_tick` for each non-spectator player, and `players_tick.mcfunction:33` calls `other/manaregen` unless `legacy=1`, `nomagic>0`, or a `stopper_magic` marker is within 20. `manaregen.mcfunction` starts `manaregen_visual` from `manaregen`, adds belt/armor bonuses, and applies the 1.5x boost transform (`*3 /2`) when `effect_boost_mana>0`. With positive visual regen, mana below max triggers one `manaregen_true` call; that helper performs one `mana += manaregen_visual` when `reverse_mana<=0`, then clamps above `manamax`. There is no second unconditional positive addition in this path, so nominal baseline is 10 units per tick (or 1 in SurvivalVersion), before item/armor modifiers. Negative visual regen also calls the helper through a separate condition. `manaregen_true_pre` is a distinct Nyauwu chest-underwater branch when mana is already full: it adds 1 and visual regen without the helper cap. The old `tick1s` schedule is not the regen cadence.

Death/respawn does not look like a fresh mana initialization: `leave_death.mcfunction` clears `reverse_mana` and temporary effect trackers (including effect add/remove mana/max/regen), but does not reset `mana`, `manamax`, `manaregen`, or `food_count`. `respawn.mcfunction` likewise does not set them; it can restore the saved `food_count` through `vanity_respawn` for Vanity holders. Thus the explicit reset values are start/new-game/first-ID initialization, not every death. `food_count` has no decay in the inspected lifecycle; it only changes through explicit food/item functions, reset, or Vanity save/restore.

## Raid Omen amplifier 40 handling and observed sources

The active generic handler is `mobs_tick.mcfunction:1`: for any non-spectator, non-time-stopped entity with active `minecraft:raid_omen`, it calls `projectiles/arrows2.mcfunction`. That function reads amplifier/duration; amplifier 40 adds the remaining effect duration to `effect_rtp_1`. `effects/tick_5t.mcfunction` runs `effects/rtp_1.mcfunction` when this score is positive; it applies `spreadplayers` at the entity (0..10, with the Nether `under 120` variant) and removes 5 score. This is a second, independent Omen-40 behavior beyond Purple's explicit spreadplayers commands.

Exact effect-give call sites with amplifier 40 in LBC functions: `other/artifact/colors/purple.mcfunction:2` applies raid omen for 30 seconds / 600 ticks to hostile non-spectator mobs within 20; `other/attributes/pills/raid_omen_40.mcfunction:1` applies it for 10 seconds / 200 ticks. The pill handler is wired as the reward in `advancement/pills/pill_raid_omen_40.json:41`. Additional non-function item data embeds amplifier 40 in `loot_table/imba/potions.json`, `loot_table/transformables_potion.json`, and `loot_table/legacy_luckyblock.json`; these are data payloads rather than additional command handlers. The many non-40 Raid Omen amplifiers use the same generic `arrows2` dispatch but map to different `effect_*` scores.
