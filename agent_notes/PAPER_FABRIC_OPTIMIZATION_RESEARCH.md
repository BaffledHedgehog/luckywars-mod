# Оптимизации Paper для SkyWars2

Продолжение исследования: [собственный алгоритм внедрён и проверен](EXPLOSION_OPTIMIZATION_PORT.md).
Ниже сохранён исходный исследовательский снимок; утверждение «Java не менялась»
относится к нему, а не к последующему переносу. По уточнению пользователя
точное сохранение RNG больше не требуется.

Исследование 16 октября 2026. Проверены официальные исходники, опубликованные
версии и наш код. Изменений Java, установок модов и нагрузочных запусков в этой
задаче не было. Подробные источники: [Paper/TNT](PAPER_TNT_SOURCE_RESEARCH.md),
[Fabric-моды и версии](FABRIC_OPTIMIZER_SOURCE_RESEARCH.md).

## Вывод

Для SkyWars2 разумны два направления: небольшие оптимизации наших массовых
взрывов и отдельное испытание готового Moonrise/Lithium. Полностью переносить
систему чанков Paper внутрь игрового мода невыгодно: это большой самостоятельный
проект с постоянным сопровождением. Наличие оптимизатора не доказывает
совместимость с нашими mixin и Polymer; измерений прироста пока нет.

Особенно подходящий готовый проект — [Moonrise](https://github.com/Tuinity/Moonrise):
его автор прямо связывает изменения с Paper. Есть [релиз v1.2.0 для 26.3](https://github.com/Tuinity/Moonrise/releases/tag/v1.2.0).
Это оптимизации столкновений, доступа к блокам/сущностям, трекинга и чанков.
В исходнике отдельно оптимизированы взрывы, а не только движение TNT.

## Что действительно делает расчёт взрыва дешевле

Сверены Paper `09ee222482646f8ed84413aea89d0108653af938`, Moonrise
`7c40258f6d625846424a8c757a0f020b6392e724` и локальный vanilla sources jar 26.3.
Это снимки исходников; версия опубликованного JAR Moonrise — отдельный релиз,
его код при испытании тоже нужно закрепить, а не считать равным текущей ветке.

| Приём | Как устроен | Решение для нас |
| --- | --- | --- |
| Направления лучей заранее | Moonrise один раз строит 1352 направления поверхности куба 16³, вместо повторных нормализаций на каждый взрыв | Хороший кандидат для собственной реализации; сохранить порядок лучей, float/double округления и вызовы RNG |
| Кэш чтения блоков/сопротивления | Moonrise переиспользует данные одной позиции для многих лучей; кэш ограничен одним взрывом, включает быстрый кэш чанков | Главный кандидат для больших взрывов; сначала профиль и ограничения применимости калькулятора |
| Жидкость из уже прочитанного BlockState | Paper заменяет отдельный `level.getFluidState(pos)` на `block.getFluidState()` | Узкое сокращение повторного поиска блока; проверить vanilla/Polymer состояния |
| Быстрая проверка укрытий | Moonrise использует обход клеток луча и кэш collision shapes для расчёта exposure | Полезно при множестве целей; контекстные формы блоков нельзя считать постоянными для всех сущностей |
| Не включать воздух в список разрушения | Moonrise добавляет воздух только при огне | Для помеченных Exasperato TNT похожий приём уже есть в `HazardPropagationMixins.Blast`; это не устраняет проход лучей по воздуху |
| Не пересчитывать exposure между совпавшими взрывами | Paper `optimize-explosions` хранит результат по центру и AABB до конца тика | Не переносить целиком: между взрывами может исчезнуть стена, а ключ этого не учитывает |
| Ускоренная физика и поиск сущностей | Общие оптимизации Moonrise/Lithium помогают существующим TNT, мобам и поиску целей | Испытывать готовый мод, вместо копирования всей инфраструктуры в SkyWars2 |

Прямой источник алгоритма: [ServerExplosionMixin Moonrise на фиксированном commit](https://github.com/Tuinity/Moonrise/blob/7c40258f6d625846424a8c757a0f020b6392e724/src/main/java/ca/spottedleaf/moonrise/mixin/collisions/ServerExplosionMixin.java).
Его кэш создаётся в начале `explode`, очищается при возврате; пересекающиеся
взрывы не используют общий межвзрывный кэш блоков. Вызов `shouldBlockExplode`
кэшируется с предположением, что результат не зависит от остаточной мощности.
При собственном переносе это предположение нельзя распространять на произвольные
кастомные ExplosionDamageCalculator: нужен известный калькулятор или fallback.
Также повреждение сущности может вызвать модовую логику изменения мира —
инвалидация при таких callbacks требует проверки даже внутри одного взрыва.

Изменение коллекции затронутых блоков может поменять порядок разрушения,
дроп и дальнейшее состояние RNG. Поэтому «тот же радиус/число взрывов» ещё
не означает побитовую эквивалентность. Не объявлять результат безопасным до
проверок TNT-цепочек, укрытий и взаимодействий с артефактами.

## Что было включено на старом сервере

Прочитаны без изменений `cringe1_21_4_skywars/config/paper-world-defaults.yml`
и `spigot.yml`: `optimize-explosions: true`, `max-tnt-per-tick: -1`,
`tnt-entity-height-nerf: disabled`, `prevent-tnt-from-moving-in-water: false`.
Значит, кэш exposure действительно был включён, а явный лимит обработки TNT —
выключен. Нельзя объяснять прежнюю скорость включённым лимитом TNT.
Проверены файлы defaults; это не аудит всех возможных world overrides.

Лимиты Spigot/Paper, изменение activation range, удаление TNT по высоте,
слияние зарядов и снижение частоты игровой логики меняют тайминги/механику.
Они не входят в предлагаемый перенос. Нулевой fuse у нас уже исполняется
через native explosion без добавления TNT-сущности, с сохранением владельца.

## Готовые варианты и порядок испытания

| Вариант | Подтверждённая версия для Fabric 26.3 | Наш приоритет |
| --- | --- | --- |
| Moonrise | v1.2.0, официальный GitHub release | Первый широкий кандидат на преимущества Paper; отдельно сравнить с чистой сборкой |
| Lithium | mc26.3-0.26.2-fabric, release | Второй самостоятельный кандидат; можно отключать отдельные группы оптимизаций |
| FerriteCore | 9.0.0-fabric, release с заявленной 26.3 | Прежде всего память и возможное уменьшение GC; не обещать ускорение самих взрывов |
| ServerCore | 1.5.20+26.3, release | Позже, с разбором каждой настройки поведения |
| VMP | 0.2.0+beta.7.238+26.3, alpha | Позже, если профиль покажет дорогой трекинг/рассылку при множестве игроков |
| C2ME | 0.4.2-alpha.0.104+26.3, alpha | Не вместе с Moonrise; сейчас не первоочередной кандидат для взрывов |

Moonrise объявляет совместимость с Lithium/FerriteCore через выключение
перекрывающихся оптимизаций, с обязательной проверкой каждой пары релизов;
C2ME прямо объявлен несовместимым. Это сведения автора, не результат нашего
совместного запуска. Не ставить весь список одновременно.

Конкретное пересечение: наш `HazardPropagationMixins.Blast` оборачивает вызовы
в `calculateExplodedPositions`, `hurtEntities`, `explode`. Moonrise отменяет
нативный `calculateExplodedPositions` своим HEAD-инжектом: старая обёртка
`shouldBlockExplode` может перестать исполняться на обычном пути, хотя точка
формально присутствует в байткоде. Проверять поведение, а не только успешный
старт без mixin error. В Lithium есть своя ветка explosion raycast, в том числе
skip-air с документированными отличиями от vanilla; детали — в заметке агента.

## План реализации и измерений

1. Сделать воспроизводимый стенд на копии одной карты: одинаковые позиции,
   блоки, сущности, входной RNG и отдельный прогрев JVM перед замерами.
   Сравнивать базовый мод, Moonrise и Lithium по отдельности. Комбинацию — позже.
2. Разделить стоимость: поиск разрушенных блоков, exposure/урон, применение
   разрушений/дроп, физика TNT и рассылка. Собирать p50/p95/p99/max времени тика,
   CPU/allocations и полный срок завершения серии. JFR позволяет начать без
   дополнительной библиотеки; расходы самого профилирования учитывать.
3. Нагрузки: 32×radius20 Nuke на плотной карте, Chaos 80 взрывов, полная дорожка
   Electro Ray 200 тиков (2600 TNT), цепочки TNT; отдельно 200–300 снарядов.
   Маленькая пустая площадка не заменяет эти сцены. Повторить несколько раз.
4. Проверить owner/монеты/сообщение смерти, 10 уникальных попаданий испытания,
   защиту команд/наблюдателей/магазина, отражение снарядов, заморозку/остановку
   времени, артефакты, Creative/developer, разрушение и дроп, отключённые caps,
   загруженные чанки, spectator camera и Polymer-пакеты. Проверить stop/epoch.
5. Если готовые оптимизации несовместимы, переносить только измеренно дорогой
   участок внутрь существующего explosion mixin: сначала повторный fluid lookup,
   затем локальный кэш чтений/направлений для известных наших TNT-калькуляторов.
   Не создавать параллельный движок боя или второй источник owner.
6. Не выполнять обращения к живому миру асинхронно. Отдельно возможен расчёт
   по неизменяемому снимку, но стоимость копирования и проверка актуальности
   способны съесть выигрыш. Деление одного взрыва по тикам меняет момент урона
   и разрушений — это отдельное решение, а не автоматическая оптимизация.

Существующие 4 мс для Nuke — мягкий бюджет **между** атомарными взрывами;
один дорогой взрыв способен его превысить. Все поставленные взрывы остаются
в очереди: лимита накопления, потери хвоста и запрета каста не добавлять (user).

Этот план задаёт дальнейшую работу, а не объявляет её выполненной. Для уже
описанных измерений в SERVER_TESTS использовались другие сцены/прогревы;
их времена нельзя выдавать за контролируемое сравнение оптимизаторов.
