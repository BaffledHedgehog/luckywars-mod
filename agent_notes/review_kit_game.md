# Независимая сверка LBC kit-game

Сверил inventory job `lbc_kit_game`, исходные функции и существующую прозу в [lbc_kit_game.md](lbc_kit_game.md). Каждой строке inventory соответствует отдельная запись с SHA-256 в [машинном аудите](inventory/lbc_kit_game_review_audit.json); воспроизвести аудит можно скриптом [audit_lbc_kit_game.py](tools/audit_lbc_kit_game.py). Статусы coverage и состояние job не менял.

| Проверка | Результат |
|---|---:|
| Источников и уникальных путей в задании | 1 355 / 1 355 |
| Числовых runtime-функций Expansion | 1 106 |
| Обычных runtime-функций | 248 |
| Python-генератор, не runtime-функция | 1 |
| Числовые ID | 1–1 106 без дыр и повторов ID |
| Разных реальных blockstate-строк | 1 104 |
| Полностью одинаковых исходных групп | 1 348 fingerprints для 1 355 строк |

Числовые функции проверены все: каждая содержит один `setblock ~ ~ ~ ...`, диапазон ID непрерывный, повторяются ровно два результата — `test_block` в ID 458 и 971, `test_instance_block` в ID 394 и 972. Следовательно случайный selector выбирает равновероятно каждый ID, а эти два blockstate получают каждый по два шанса из 1 106. Динамическая цепочка `place_random_block` сначала проверяет `chance1` (1%), затем `random value 1..1106` и вызывает ID через макрос из `storage lbc.math`; шанс любого конкретного ID на один такой проход равен `0.01/1106`.

`blockgen.py` не является runtime-механикой. Его 1 106 значений отличаются от реальных файлов в ID 394 и 458: runtime содержит соответственно `test_instance_block` и `test_block`, а список генератора — `glow_item_frame` и `item_frame`. ID 165 в генераторе записан как `iron_chain`, что эквивалентно runtime `minecraft:iron_chain`. Генератор открывает каждый ID-файл в append-режиме и пишет новую полную команду с `strict`; 1 105 текущих файлов не имеют завершающего newline, так что повторный запуск склеил бы вторую команду с первой в повреждённую строку. ID 967 имеет завершающий newline и получил бы отдельную команду, но `strict` не является допустимым режимом `setblock`. Генератор не запускался.

Проверены важные selector- и execution-контракты, которые влияют на фактический результат:

- `kit_select/select` и `skill_select/select` ведут команды от выбранного игрока `@s`, но берут имя в общий временный блок и пишут поля в глобальный `storage stats:stats`. Внутри datapack цепочки идут синхронно; статистика выбора не сохраняется после `game_started=1`. Выбор skill дополнительно очищает/ставит `manavampire`, вызывает `erose` для skill 5 и сбрасывает цвет Rainbow Aura для skill 32.
- Levelup и trinket scores содержат до четырёх двухзначных ID каждый; три score дают до 12 позиций, фактическое число вызовов ограничивают `#lbclevelupmax` и `#lbctrinket`. ID 14 имеет десять последовательных повторных бросков при повторном результате 14 и тег `perk_random`, который разрешает только один reroll за пересчёт. Если десятый бросок всё ещё 14, ветки эффекта для 14 нет. Статистические macro/storage helpers используют общие storage, но вызываются в текущем контексте игрока.
- Trinket pass переносит найденные в hotbar слоты 0–8 предметы с `custom_data.trinket` в inventory slots начиная с 4. Helper не проверяет пустоту целевого слота: он заменяет там прежний предмет и очищает hotbar-слот.
- `challenge_content_select` вызывает отдельные challenge selector-ы. В проверенных источниках только `challenge_kit_select` делает действие — сохраняет `x_kit` до старта игры и выдаёт `academy_token` при `lbc.challenge.kit=1`; challenge-levelup и challenge-trinket файлы пусты, обычные selector-ы этим entrypoint не вызываются.
- Общие временные shulker buffers, используемые selection helpers и PHD crafting, заранее создаются и force-load-ятся из `load.mcfunction`; PHD buffer в частности находится на абсолютной координате `10241024 94 10241024`. Значит его временные координаты и глобальный storage реальны, но не зависят от позиции игрока.
- `execute store result score ... if entity` в `expansion_active`, `god_claw_active` и `simbiont_damaged` даёт число совпавших сущностей. Первые две функции считают принадлежащие игроку markers; Simbiont делит `blocked_damage` на число принадлежащих мобов. Это count, не boolean.

Проверка PHD kit обнаружила важную потерю деталей в прежнем тексте. Триггер требует минимум три из четырёх crafting slots с `#minecraft:bioitems`, а не фиксированный рецепт; каждую найденную стопку функция пропускает через координатный block buffer, хеширует символы ID с позиций 10–37, складывает их с `#game_seed`, берёт `%144` и выдаёт `lbc:kit/pill`. Из каждого подходящего ингредиента тратится по одному предмету, остаток стопки возвращается в тот же crafting slot. Score `currhash` не сбрасывается между символами и craft-вызовами; незакодированные цифры/знаки сохраняют предыдущий код символа, включая значение от предыдущего игрока. Исправил описание PHD в основном документе.

Для Expansion сверены startup, tick, восемь направленных ветвей marker continuation, cleanup, selection predicate и все 1 106 реальных blockstate-функций. В основной текст добавлены не очищаемые при конце блоки, удаление `Items` у block entity под marker, cooldown-score, равномерные дубли `test_block`/`test_instance_block` и точный риск повторного запуска `blockgen.py`.

Наконец, в Simbiont обнаружена исполняемая команда `kill @s` после записи `Health×10`, если score `lucky_block_count` ≤10 000 000. Это соответствует обычным mob с Health≤1 000 000 и удаляет их на player-tick при совпадающем `lbcID2`, если внешний helper не поднял их здоровье выше порога. Обратный damage-pass делит blocked damage на **количество** связанных mob; при нуле targets урон не выполняется. Этот фактический эффект и осторожную границу внешней подчиняющей функции добавил в основной документ.

После правок `check_coverage.py` прошёл: 10 800/10 800 источников имеют рабочие ссылки; unresolved и link errors — 0.
