# CPU event review: lobby entity cleanup

## Current implementation review

`ServerEntityEvents.ENTITY_LOAD` queues non-player entities only while `GameController.inLobby()` ([SkyWars2.java:55-57](../src/main/java/me/skywars2/SkyWars2.java#L55)). Fabric's cached `ServerEntityEvents.java` documents ENTITY_LOAD as running after the entity is already in the level; local source is [`fabric-lifecycle-events-v1-4.1.9+ffef5f675d-sources.jar`](C:/Users/yarik_temp/.gradle/caches/modules-2/files-2.1/net.fabricmc.fabric-api/fabric-lifecycle-events-v1/4.1.9+ffef5f675d/317cd5f8ba0f6c6ac5285d436baef14ed365040b/fabric-lifecycle-events-v1-4.1.9+ffef5f675d-sources.jar), entry `net/fabricmc/fabric/api/event/lifecycle/v1/ServerEntityEvents.java`. Deferring predicate evaluation to cleanup lets synchronous callers finish adding source tags after `addFreshEntity`.

`MapManager.cleanupLobbyEntities()` drains event candidates each lobby tick, checks `isRemoved()` before acting, preserves the original arena identity/tag/cloud predicate, and performs a full loaded-entity audit on entry and every 20 calls ([MapManager.java:509-545](../src/main/java/me/skywars2/game/MapManager.java#L509)). The audit covers entities loaded during `LOADING` (callbacks are intentionally ignored outside a ready lobby) and finds missed/pre-existing loaded entities. Subsequent loads are caught by the event. The `isRemoved()` guard safely skips queued references explicitly unloaded/discarded before drain; only one tick of pending lifetime is expected. Transition into or out of `LOBBY` resets both queue and audit counter; shutdown does too ([GameController.java:576-581](../src/main/java/me/skywars2/game/GameController.java#L576), [MapManager.java:547-551](../src/main/java/me/skywars2/game/MapManager.java#L547)).

`GameChecks.checkLobbyRules` now covers tag assignment after add, preserving an already-tagged entity until the audit, eventual removal after direct tag clearing, immediate event-driven removal of an untagged addition, and cross-dimension removal ([GameChecks.java:263-310](../src/main/java/me/skywars2/game/GameChecks.java#L263)). These checks align with the bounded behavior. No correctness blocker found in the reviewed cleanup edits. The observable behavior change is intentional: a post-load whitelist/tag edit may leave an entity for at most 20 lobby cleanup calls, rather than being reconsidered on every tick.

The every-tick scan was existing behavior, not a stated `(user)` requirement; the user CPU note prioritizes reducing repeated work and favors event handlers. Inventory enforcement still runs every tick and should remain a separate decision because it repairs arbitrary server-side grants/stack mutations; packet and pickup hooks cover only client paths.
