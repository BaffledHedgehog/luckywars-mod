# Indirect kill attribution audit (Minecraft 26.3)

Read-only audit, based on local merged 26.3 Minecraft sources and Fabric API 0.161.0+26.3 sources. No code/build/server changes.

## Vanilla credit state and downstream uses

- `LivingEntity.setLastHurtByPlayer(Player, int)` / `setLastHurtByPlayer(UUID, int)` are public; setter stores `lastHurtByPlayer` plus a tick countdown. `setLastHurtByMob(LivingEntity)` is public and stores a mob reference/timestamp. Tick clears player credit when its memory reaches zero; mob credit expires after 100 ticks or if that mob dies.
- `LivingEntity.getKillCredit()` returns last player hurt (if resolvable), else last mob hurt. Vanilla `hurtServer` calls `resolveMobResponsibleForDamage(source)` and `resolvePlayerResponsibleForDamage(source)`; direct `DamageSource.getEntity()` attribution therefore already updates the state, and player damage gets a 100-tick window.
- In `LivingEntity.die(source)`, vanilla calls `getKillCredit()` and `killer.awardKillScore(victim, source)` before loot. This is the all-LivingEntity native scoring/advancement path. `dropAllDeathLoot` marks loot as player-killed when `lastHurtByPlayerMemoryTime > 0` and only awards ordinary mob XP when that memory is positive (unless the mob always drops XP). Death-message text is generated from `CombatTracker`'s recorded damage sources, not `getKillCredit`; keep the environmental source type if the desired message should remain FALL/VOID/IN_WALL.
- `LivingEntity.dropExperience` passes `source.getEntity()` to `getExperienceReward`, even if `getKillCredit()` points at a recent player. Attribution through last-hurt state enables ordinary player-kill loot/XP eligibility and kill score, but enchantment-based XP bonuses may not see that player for an environmental final source.
- `ServerPlayer.die` also reads `getKillCredit()` for killer stats, native kill score and wither-rose handling. Current `GameController.died` differs: it only awards match kill stats/reward if `damage.getEntity()` is a participant `ServerPlayer` (GameController.java:510–518). It should consult `player.getKillCredit()` for fall/void/in-wall/environmental-final kills, while retaining the participant/self checks.

## Fabric event timing: not a universal attribution hook

Fabric `ServerLivingEntityEvents.ALLOW_DAMAGE` runs before damage and can only allow/cancel. `AFTER_DAMAGE` runs at `hurtServer` tail but is explicitly not fired when that hit kills. `AFTER_DEATH` runs inside `die`, at the `broadcastEntityEvent` invoke, after native killer scoring and death loot/XP have already been processed. So setting last-hurt credit from these callbacks is too late for native rewards on a lethal hit (AFTER_DEATH can still support post-death match stats). `ServerEntityCombatEvents.AFTER_KILLED_OTHER_ENTITY` wraps the source entity's `killedEntity` call during `die`, also after the earlier vanilla `awardKillScore` decision.

## Appropriate attribution point

Use the existing last-hurt credit fields, not fake damage or a replacement `DamageSource`: call `victim.setLastHurtByPlayer(owner, memoryTicks)` for player-caused environmental danger, or `setLastHurtByMob(attacker)` for mob-caused danger, before the victim's fatal damage resolution. This preserves the actual FALL/VOID/IN_WALL/status `DamageSource`, armor/knockback behavior, CombatTracker message/type, and vanilla `getKillCredit()` consumers. A mixin around `LivingEntity.resolvePlayerResponsibleForDamage` / `resolveMobResponsibleForDamage` can apply a stored contextual cause immediately before the fatal decision; a source-specific hazard/ability hook is better when its causative player is known. If using `getKillCredit` injection, it must also establish `lastHurtByPlayer` before `dropAllDeathLoot` so the player-killed memory check and XP gate work.

- TinyTeleport levitation: record the caster when applying/refreshing the levitation; associate falling damage while that owned effect is active, ideally in its damage-resolution context. A bare 100-tick last-hurt marker is insufficient if levitation/fall is delayed beyond 5 seconds.
- TinyRuby support break: at the owned block-break event, identify affected entities whose fall was caused by that support loss and retain the breaker as their cause until fatal fall damage; merely crediting the block break does not itself cause later damage.
- TinyStone placed blocks: attach placer identity to the placed-block hazard, then attribute the resulting `IN_WALL` damage at fatal damage resolution; don't replace the suffocation source.
- Acid wand periodic effects: vanilla `PoisonMobEffect.applyEffectTick` calls `mob.hurtServer(level, mob.damageSources().magic(), 1)` and `WitherMobEffect` uses `damageSources().wither()`—neither source has the original applier. `LivingEntity.addEffect(instance, source)` receives the source entity but does not persist it in `MobEffectInstance`; capture effect→owner when applied and refresh/set player credit on periodic owned effect damage. Fabric `ServerMobEffectEvents` callbacks expose the effect/context but not the source entity, so they alone cannot recover the applier. Apply same owner capture to any acid-applied fire effect/ignition; later fire tick damage likewise has no source actor.

The key constraint for all four cases is causality: store the originating player at the action/effect application, then set native last-hurt credit before fatal damage. Do not infer a player from the final environmental damage type, and do not set a stale credit on unrelated hazards.
