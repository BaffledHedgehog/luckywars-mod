# Документация исходных datapack SkyWars

Актуальная папка документации — `E:/servers_mew/skywars2_last/luckywars-mod/agent_notes`.
Исходный сервер и Java-реализации остаются в `E:/servers_mew/cringe1_21_4_skywars`.
Пометки `(user)` имеют приоритет над агентскими выводами и сохраняются дословно.
Если пометка задаёт желаемое изменение, оно отдельно учитывается как требование,
а фактическое поведение существующего кода описывается рядом. Правила:
[AGENTS.md](AGENTS.md).

Исследование расширено на `plugins/luckywars` и `mods/luckywarsignite`:
обработчики команд, предметные слушатели и native/legacy runtime.
Приёмка 35 заданий ниже относится к первоначальному снимку datapack.

Исходники datapack: `world/datapacksdisabled/LBC`, `maps` и `swarogskywars`.
Их поведение описано отдельно от Java-реализаций старого сервера. Для команд,
предметных слушателей и native/legacy runtime также изучены `plugins/luckywars`
и `mods/luckywarsignite`; эти реализации могут расходиться с datapack.
Папки отключены на сервере; «текущее поведение» здесь означает поведение при
исполнении данного набора datapack. Различия с работающим сервером не подменяем догадками.

Приёмка завершена: **35 заданий, 10 800 источников**. Подтверждения —
[COMPLETION_AUDIT.md](COMPLETION_AUDIT.md).

## Правила для исследователей

1. Писать на русском, простыми словами. На отдельный предмет/механику — обычно
   2–6 предложений: как активировать, что происходит, условия/ресурс/откат,
   как заканчивается, важные связи с другими механиками.
2. Давать точные идентификаторы предметов/функций и ссылки на исходники.
   Комментарии и lore проверять по исполняемым командам.
3. Не смешивать название предмета, его vanilla-основу, custom_data и модель.
   Если идентификация неоднозначна, перечислить ключи и отметить неясность.
4. Прослеживать вызываемые функции, advancements, predicates, loot tables,
   item modifiers, scheduler, scoreboard и storage до фактического эффекта.
5. Объяснять состояния load/tick/start/end/reset и межпакетные связи.
   Изменяющие поведение ошибки, мёртвый код и неизвестные внешние зависимости
   отмечать отдельно; не придумывать ожидаемую реализацию.
6. Одинаковые сгенерированные варианты объединять только после проверки общего
   шаблона. Указывать различающиеся параметры и все варианты в таблице/приложении.
7. Каждый исследователь пишет собственные Markdown-файлы. Не изменять чужие
   документы, datapack, серверные настройки или код мода.
8. По назначенным файлам сохранять `coverage/<имя>.json`: список объектов
   `{source, document, section, status, note}`, пути от корня репозитория.
   Допустимые статусы: `documented`, `generated_variant`, `asset`, `non_runtime`,
   `unresolved`. Статус означает реальное исследование, а не просто наличие файла.
   Нерешённые зависимости перечислять и в Markdown.
9. Не объявлять полный разбор завершённым, если отдельные предметы или ветки
   описаны только общим списком названий/папок. Сообщать начальнику о пробелах.
10. Сохранять условия каждой существенной ветки, вероятность, расход и `return`.
    Список первых пяти действий не является описанием функции с 64 результатами.
    Одинаковые альтернативы сводить в таблицу с полным набором вариантов.

`inventory/research_jobs.json` разделяет все исходники на непересекающиеся задания.
`inventory/loot_item_index.json` содержит точные item/loot-table entries, условия
и функции из loot tables. Это вспомогательный индекс, не описание поведения:
вес отдельного entry не равен его конечной вероятности, а lore не заменяет эффект.
Сырые JSON и контексты вызова проверяются исследователем отдельно.

Исполняемая `.mcfunction` без найденного автоматического вызова всё равно имеет
поведение при ручном запуске: описать её команды и отдельно отметить отсутствие
найденного триггера. `non_runtime` предназначен для вспомогательных скриптов,
настроек редактора и пустых/no-op ресурсов, а не для исключения неудобных веток.
На Windows создавать русскоязычные файлы через UTF-8-файл скрипта либо PowerShell/.NET;
передача русского Python-кода через стандартный ASCII-pipe может заменить текст
вопросительными знаками. Для корректного просмотра вывода Python: `python -X utf8 ...`.

## Проверка документации

Для контроля документации используйте `tools/check_coverage.py` (точные источники
и заголовки), `tools/check_behavior_sections.py` (пустые связанные разделы),
`tools/check_markdown_links.py` (пути ссылок) и `tools/audit_source_snapshot.py`
(сохранность исходников). Прохождение этих проверок дополняет чтение поведения;
оно не заменяет содержательную приёмку из `REVIEW.md`.

Для дополнения Paper/Ignite есть `tools/audit_java_extension.py`: он проверяет
SHA и принадлежность файлов к исследовательским manifests. Содержательная
сверка Java-обзоров отражена в [JAVA_EXTENSION_REVIEW.md](JAVA_EXTENSION_REVIEW.md).

После переноса проверки запускаются из каталога нового Fabric-проекта.
Корни старых исходников заданы в [source_roots.json](inventory/source_roots.json);
coverage сохраняет исходные идентификаторы. Старые генераторы и одноразовые
скрипты исправления оставлены как история исследования: их повторный запуск
может перезаписать ручной текст, поэтому они не входят в поддерживаемые проверки.

## Встраивание данных в новый Fabric-мод

Основное место: `E:/servers_mew/skywars2_last/luckywars-mod/src/main/resources/data/`.
Копировать содержимое `data/` datapack, сохраняя namespace и структуру каталогов.
Например: `data/lbc/function/`, `data/swrg/loot_table/`,
`data/minecraft/tags/function/load.json`, `data/swrg/structure/`.
Для обычных данных мода отдельный `pack.mcmeta` каждого пакета не переносится.
При объединении одинаковых путей, особенно тегов `load`/`tick`, требуется
содержательное объединение. Фильтр из `swarogskywars/pack.mcmeta` не переносится
автоматически вместе с `data/` и должен рассматриваться отдельно.

Это только место размещения: совместимость команд и данных старых пакетов с
Minecraft 26.3 надо проверять при переносе. В ходе исследования сами данные
в новый мод не копируются.
