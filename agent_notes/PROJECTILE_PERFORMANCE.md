# Снаряды: попадания и нагрузка

Актуальные замеры обычного и Academy Terra:
[проверки и условия](TERRA_ACADEMY_CHECKS.md). На JAR `5cc324db…` при
300 зарядах с моделями/частицами — 20 TPS, средние 1,7/1,5 MSPT в двух
изолированных сценариях с fake-подключениями. Ниже сохранены более ранние
исследования Tiny Terra и кислоты; прежний замер 1,2 MSPT на `341c6293…`
описан отдельно в [архиве обычного Terra](TERRA_REGULAR_CHECKS.md).

## Требование и решение пользователя

Целевая нагрузка — 200–300 одновременных снарядов, без прежнего падения TPS
от командных raycast-циклов. Само число сущностей не определяет стоимость:
важны типы снарядов, их плотность, число целей, рассылки и прочая нагрузка мира.

На вопрос о нативном пересечении отрезка движения с хитбоксом вместо sampled
кубиков 1×1×1 пользователь ответил (user):

> Да, нативное попадание по хитбоксу

Это разрешает сменить геометрию попадания. Само по себе решение не меняет
скорость/траекторию всех жезлов, не превращает мгновенные лучи в летящие
снаряды и не разрешает сокращать эффекты или их частоту.

## Что сейчас в коде

Tiny Terra — мгновенный луч длиной 35 блоков, а не постоянно тикающая сущность.
Раньше один spatial query собирал кандидатов, затем до 101 samples повторно
перебирали их. Теперь `ProjectileUtil.getManyEntityHitResult` получает цели
одним запросом и проверяет один отрезок против каждого хитбокса. Margin = 0;
цели, содержащие начало отрезка, учитываются. Первая sampled-стена ограничивает
отрезок своей передней границей; цель за ней не поражается. Каждая цель получает
одну попытку 5 cactus-урона; нативная неуязвимость не сбрасывается. Стрелок,
союзники и настоящие/Adventure-наблюдатели исключены прежним общим фильтром.

До 101 samples остаются для прежних частиц, звука и поиска стены. Стоимость
геометрии попадания больше не умножается на это число; это вывод по коду,
а не измеренное ускорение всего тика. Малые Blind/Air/Stone/Teleport/Acid
пока сохраняют прежний sampled ray; новая политика должна применяться при
их последующей переработке с адресной проверкой endpoints.

Кислота уже является настоящим `ThrowableProjectile` с нативными gravity,
drag и swept collision. Нативный поиск ограничивает кандидатов пространственными
секциями, затем пересекает отрезок движения с их хитбоксами. Но кислота имеет
дополнительную ауру: каждый тик ищет щиты, источники огня и living-цели.
Плотная группа кислоты может многократно проверять соседние снаряды при
поиске огня. Поэтому 300 таких объектов не эквивалентны 300 обычным стрелам.
Подробности: [аудит](PROJECTILE_PERFORMANCE_AUDIT.md).

Обычная и Academy Terra перенесены в общий `LbcTerra`. В старом datapack это persistent
marker rays с максимумом 7/26 samples за тик и новыми selectors на шагах.
[Сверка исходника и разделение версий](TERRA_PROJECTILE_SOURCE_COST.md).

## Дальнейший перенос

Новые уточнения пользователя: [модели Terra](TERRA_PROJECTILE_MODELS.md)
и [политика дальнего полёта](PROJECTILE_LIFETIME.md). Границы структуры карты
не ограничивают бой или lifetime: большие координаты за картой поддерживаются.
Кислота и снаряды Terra Sword сохраняют намеренную конечность.

1. Для летящих снарядов переиспользовать нативные projectile ticks и swept
   collision. Для пробивающих — один native many-hit запрос на отрезок
   перемещения за тик. Не сканировать весь мир и не запускать команды
   selectors на каждом мелком шаге. Нативные spatial sections уже существуют;
   отдельную сетку не добавлять без измеренной необходимости.
2. Отделять визуальный след от collision: точки частиц могут идти вдоль
   отрезка без повторного поиска сущностей. Сначала сохранять дизайн.
3. Дополнительные ауры/наведение профилировать отдельно. При подтверждённой
   стоимости исследовать общие candidate snapshots и объединение одинаковых
   записей, сохраняя щиты, распространение огня и независимые damage events.
   Снижение частоты поиска/урона или количества частиц требует согласования.
4. Сохранять владельца, фильтры команды/наблюдателей, lifetime, loaded-chunk
   guards, match epoch и cleanup на stop. Обычный projectile не должен
   подгружать карту ради продолжения полёта.
5. Коллизии, чтение/изменение мира и урон остаются на server thread.
   Передача сотен коротких проверок рабочим потокам сама создаёт затраты и
   гонки; выносить только подтверждённые тяжёлые чистые расчёты по снимкам.

### Нагрузочный сценарий

`tools/benchmark_projectiles.py --server-dir build/verification/key-reuse-server`
и тот же запуск с `--targets 32` выполнили 12 сценариев на этом же JAR.
После создания каждой группы проходит 120 настоящих серверных тиков;
консольный `tick query` получает среднее и p50/p95/p99 последних 100 тиков.
Тики не ускорялись и не вызывались вручную. Spawn-команды остаются вне окна
100 samples. Число существ проверяется после прогрева; для targets-пути
дополнительно подтверждено наличие poison у живой цели.

Условия: Ryzen 7 5700X, Windows, JDK 25, JVM Xms1G/Xmx4G, view/simulation
distance 4, карта 1, два фиктивных ServerPlayer в Creative. У кислоты нет
владельца (ветка обычной химической кислоты), `NoGravity=1`, начальная скорость
`(0.03,0,0)` с нативным drag: так группа сохраняется до конца окна и не
исчезает из-за земли. Custom aura и нативный entity tick работают. Sparse —
шаг 5 блоков; dense — 0,8 по X/Z и слои по 0,5 Y. В targets-пути 32 cow
имеют NoAI/NoGravity/Invulnerable, стоят ниже физического пути, в зоне ауры;
повторное наложение poison выполняется, урон и смерть не моделируются.
Временный datapack и forced chunks убраны, конфиги тестового сервера возвращены.

| AcidProjectile | Разнесённо: среднее / p99, мс | Плотно: среднее / p99, мс | Плотно, 32 цели: среднее / p99, мс |
| --- | --- | --- | --- |
| 0 | 1,3 / 2,8 | 0,6 / 1,1 | 2,3 / 7,1 |
| 100 | 1,2 / 1,9 | 0,9 / 1,4 | 1,4 / 2,4 |
| 200 | 1,0 / 1,8 | 1,3 / 1,9 | 1,6 / 2,1 |
| 300 | 1,3 / 2,7 | 1,7 / 2,3 | 2,0 / 2,9 |

Все сценарии показывали 20 TPS. Для 300 с 32 целями p50 = 2,0 мс,
p95 = 2,3 мс, p99 = 2,9 мс. Одно короткое окно на случай, фиксированный
порядок и JIT/background noise видны по отличающимся baseline: нельзя
интерпретировать разницу соседних строк как точную цену одного projectile.

Проверенный факт — 300 объектов выдержаны в этих сценариях; максимум сервера
не определён. Это не замер каста Terra, не сравнение скорости с datapack и
не полноценный бой. Нет реальных клиентов/сетевой отправки, быстрого длинного
перелёта, горящей кислоты, массовых hurt hooks и остальной нагрузки матча.
Для 20 TPS бюджет тика 50 мс; нужен запас для этих механизмов.

Данные: `build/verification/projectile-benchmark{-targets,}-results.json`,
одноимённые `.log`; в JSON сохранены native query output, JAR SHA и SHA лога.
Дальнейшие изменения аур/наведения проверять той же методикой, расширяя
боевые сценарии по мере переноса.
